PART 2: STRICT TECHNICAL REVIEW

1. Memory Accounting and Math Inconsistencies

- ps/top %MEM calculation error ([P-L2], [P-L3], [FR-L1]):
  Total RAM is 3933 MiB = 4,027,392 KiB ([FR-L1]). Java RSS is 1,884,312 KiB = 1,840.15 MiB ([P-L3], [P-L1]).
  1,884,312 / 4,027,392 = 46.79% (46.8% in top, 46.7% in procps ps), NOT 47.9%. The transcript mistakenly divided decimal MB (1884.312) by MiB (3933) to get 47.9%.

- NMT Total does not equal the sum of listed categories ([N-L1]-[N-L9]):
  Summing [N-L2] through [N-L9] gives reserved = 3,437,993 KB and committed = 2,261,341 KB, leaving 1,234,127 KB (~1.18 GiB) of reserved memory and 100,503 KB (~98 MiB) of committed memory unaccounted for relative to [N-L1] (reserved=4,672,120 KB, committed=2,361,844 KB). While NMT summary has other categories (Compiler, Arena Chunk, NMT, Module, etc.) that appear omitted, they do not account for 1.18 GiB of reserved space or ~98 MiB of committed space.

- NMT Class reserved is smaller than GC.heap_info Metaspace reserved ([N-L3] vs [H-L2]):
  [H-L2] reports Metaspace reserved = 1,114,112 KB, whereas [N-L3] reports Class reserved = 1,067,301 KB (46,811 KB less). In HotSpot NMT where Class encompasses Metaspace (non-class + compressed class space), Class reserved must be >= Metaspace reserved. (Also, if Metaspace were tracked separately from Class, the ~1.11 GB Metaspace reserved and ~93 MB committed almost match the exact missing gap in [N-L1], implying Metaspace was double-counted in Total while still appearing under Class.)

- NMT committed (2,361,844 KB) impossibly exceeds OS RSS (1,884,312 KB) with 0 swap ([N-L1], [P-L1], [FR-L2]):
  The gap is 477,532 KB (~466 MiB) with zero swap. While untouched committed mmap pages do not count toward RSS, here:
  (a) Direct buffers in Other ([N-L8], 926,981 KB) are zero-initialized on allocation by ByteBuffer.allocateDirect / Unsafe.setMemory, so 100% are resident.
  (b) Java Heap ([N-L2], 1,048,576 KB) has -Xms1g -Xmx1g ([P-L3], [P-L4]) and has survived 211 Young GCs and 8 Concurrent Cycles ([H-L3]) with peak usage >= 702 MiB ([G-L3]). G1GC cycles through free regions and does not uncommit when Xms == Xmx, so nearly the entire 1024 MiB heap has been dirtied and is resident. Even using the unrealistically low floor of 702 MiB (718,848 KB) touched heap, plus 926,981 KB direct, 92,011 KB used Metaspace ([H-L2]), 44,120 KB Code, 60,932 KB GC, 28,917 KB Symbol, 1,204 KB Internal, and 28,774 KB SHR ([P-L2]) already sums to 1,901,787 KB > 1,884,312 KB RSS before counting Thread stacks, glibc malloc overhead, or the remaining ~322 MiB of touched heap. Realistically RSS would be ~2.2-2.3 GiB.

- Synthetic constant-offset formula in memstat.log and impossible RSS shrinking under -Xms1g ([M-L1]-[M-L18]):
  Every single one of the 18 rows in memstat.log satisfies the exact equation:
  rss_mb = heap_used_mb + direct_mb + 370.
  This is physically impossible on a JVM with -Xms1g -Xmx1g:
  (a) In [M-L1]-[M-L4] (v2.3.0 running for 6 days), rss_mb drops from 971 to 945 and from 1022 to 991 in lockstep with heap_used_mb (540->515, 590->560). G1GC with Xms == Xmx never returns freed heap pages to the OS between young GCs, so RSS does not fall 1-to-1 when heap_used drops.
  (b) A 6-day-old JVM with -Xms1g (1024 MiB) + ~92 MiB Metaspace + ~44 MiB Code + ~61 MiB GC + ~61 MiB direct cannot have RSS = 945 MB ([M-L2]).
  (c) Ten minutes after [M-L18] (at 06:40:12), the implied overhead suddenly drops from 370 MB to 322.9 MiB (1840.15 MiB RSS - 612 MiB heap_used - 905.25 MiB direct).

- dmesg OOM total-vm vs anon-rss growth contradiction ([K-L2], [K-L5] vs [P-L3]):
  Between 06:40:12 (PID 24817, [P-L3]) and OOM kill (PID 11820 [K-L2], PID 19044 [K-L5]), anon-rss grew by +1,676,896 KB (to 3,561,208 KB) and +1,728,032 KB (to 3,612,344 KB) due to ~1.6-1.7 GB of additional direct buffer allocations. However, total-vm only increased by +634,184 KB (7,078,300 -> 7,712,484 KB) and +719,820 KB (7,078,300 -> 7,798,120 KB). New malloc/mmap direct buffer allocations expand virtual address space at least 1-for-1 unless >1 GB of empty virtual arena space was already pre-mapped at 06:40.

- dmesg file-rss:0kB twice on the executing process ([K-L1]/[K-L2], [K-L4]/[K-L5]):
  Both OOM kills report file-rss:0kB on the java process that itself invoked the OOM killer. While extreme reclaim can drive file-rss very low, a process actively executing code in java/libjvm.so/libc.so having exactly 0 kB of file-backed pages on two separate occasions is highly implausible.

- NMT Thread reserved == committed ([N-L4]):
  Thread reports reserved=52398KB, committed=52398KB identically. On Linux with Java 17 (JDK-8191369), NMT tracks actual committed thread stack pages separately from reserved 1 MB stack mappings, so committed is normally a small fraction of reserved.

- Leak rate in memstat.log does not correlate with receipts_upload traffic in access-hourly.log ([M-L5]-[M-L18] vs [X-L5]-[X-L8]):
  Hour 00 ([X-L5]): 411 uploads, direct grew +735 MB (95->830) = 1.79 MB/upload.
  Hour 02 ([X-L6]): 228 uploads, direct grew +760 MB (1560->2320) = 3.33 MB/upload.
  Hour 04 ([X-L7]): 244 uploads, direct grew +990 MB (650->1640) = 4.06 MB/upload.
  Hour 06 06:00-06:40 ([X-L8]): 402 uploads, direct grew +675 MiB (230->905) = 1.68 MiB/upload.
  When receipt upload volume dropped nearly in half overnight (411 -> 228 -> 244), the hourly direct-memory leak rate actually increased (+735 -> +760 -> +990 MB/hr), and when uploads surged back to a ~603/hr pace at 06:00, leak-per-upload dropped 2.4x.

- systemd Memory: 1.8G ([SYS-L3]) vs process RSS 1.80 GiB ([P-L1]):
  Cgroup memory.current reported by systemctl status includes process anon RSS plus cgroup-charged page cache (jar, shared libs, log writes) and kernel slab memory, so it would typically exceed raw process RSS (1.80 GiB) rather than matching it identically.


2. GC and Heap State Contradictions

- gc.log exists despite NO GC logging flag on the JVM command line ([G-L1]-[G-L3] vs [F-L1], [P-L3], [P-L4]):
  ExecStart ([F-L1]) and ps ([P-L3]) pass only -Xms1g -Xmx1g -XX:MaxDirectMemorySize=3g -XX:NativeMemoryTracking=summary -jar .... There is no -Xlog:gc*:file=/var/log/point-api/gc.log flag, yet /var/log/point-api/gc.log contains Java 17 unified GC logs from the current PID.

- Mathematical impossibility between jstat -gcutil ([H-L3]) and jcmd GC.heap_info ([H-L1]):
  [H-L1] reports total heap = 1024 regions (1,048,576 KB), used = 612 regions (626,688 KB), young = 212 regions (217,088 KB), survivors = 9 regions (9,216 KB), meaning Eden used = 203 regions (207,872 KB) and Old used = 400 regions (409,600 KB).
  [H-L3] reports S0=0.00%, S1=100.00%, E=27.51%, O=56.80%.
  First, in G1GC, EC + S1C + OC = 1024 regions, so EC + OC = 1015 regions. With E=27.51% and O=56.80%, the maximum possible EU + OU is strictly less than 56.80% * 1015 = 576.5 regions; adding 9 survivor regions gives at most 585.5 regions (599,572 KB), making 612 regions (626,688 KB) in [H-L1] and [C-L2] mathematically impossible.
  Second, dividing [H-L1]'s Eden used (203) by 0.2751 gives EC = 738 regions and Old used (400) by 0.5680 gives OC = 704 regions, totaling 1,442 regions (> 1,024 total heap regions).

- Contradiction between gc.log ([G-L1]-[G-L3]) and GC.heap_info ([H-L1]) / jstat ([H-L3]):
  (a) At 06:39:41 ([G-L3]), GC(211) finished with 588M used (Old + Survivor, Eden = 0M). At 06:40:12 (31s later, with YGC still at 211 in [H-L3], meaning no GC occurred in between), [H-L1] shows Old + Survivor = 409M (400M Old + 9M Survivor) and Eden = 203M. Old Gen cannot drop by 179M without a GC, nor can Eden reach 203M when [G-L1]-[G-L3] show Young GCs consistently firing when Eden fills by only ~114-119M (579M->701M, 583M->702M).
  (b) GC numbering mismatch: HotSpot unified logging is 0-indexed (GC(0) is the first GC) and assigns separate GC(N) IDs to G1 concurrent mark cycles (CGC=8 in [H-L3] corresponds to 4 concurrent cycles in Java 17 since jstat counts both Remark and Cleanup in CGC). Thus the 211th Young GC would not be GC(211) (it would be ~GC(214), or GC(210) even without CGC IDs).
  (c) GC cadence mismatch: [G-L1]-[G-L3] show ~49-50s between Young GCs during peak 06:38-06:39 traffic ([X-L8]), which implies ~64 Young GCs over 53 minutes—far below YGC=211 (which averages 1 YGC every 15 seconds).

5. JVM Flag Semantics, Netty vs JDK Direct Buffers, and Spring Boot Actuator

- MaxDirectMemorySize=3g misconfiguration on a 4 GB swapless host ([F-L1], [P-L3], [P-L4], [FR-L1], [FR-L2]):
  With -Xmx1g (1 GiB) + -XX:MaxDirectMemorySize=3g (3 GiB) + ~300-400 MiB JVM native overhead + OS/daemons (~300-400 MiB) on 3933 MiB RAM with 0 swap, the JVM's direct memory limit can never be reached. The kernel OOM killer will always kill the JVM before Bits.reserveMemory throws OutOfMemoryError: Direct buffer memory (which is why app.log has no OOM stack trace). Leaving MaxDirectMemorySize=3g unaddressed in Q4 R2 leaves this trap intact.

- Conceptual mismatch between JDK DirectByteBuffer, Netty ByteBuf, Actuator, NMT, and R2's "buffer release" diagnosis ([C-L1], [N-L8], [D-L4], Q4 R2):
  (a) Standard Spring Boot Servlet filters (RequestBodyLoggingFilter, e.g., ContentCachingRequestWrapper) buffer request bodies in on-heap byte[] arrays, not direct buffers.
  (b) If this is Spring WebFlux / Netty where buffers require explicit .release() (matching Q4 R2), Netty's PooledByteBufAllocator normally allocates 4 MiB or 16 MiB PoolChunks—not 21,877 small ~42.4 KB mallocs ([N-L8] malloc=926981KB #21877). Furthermore, when Netty uses allocateDirectNoCleaner() (Unsafe.allocateMemory directly), those buffers are NOT counted by BufferPoolMXBean / Micrometer jvm.buffer.memory.used?tag=id:direct ([C-L1]). (On Java 17 without --add-opens java.base/java.nio=ALL-UNNAMED, Netty falls back to ByteBuffer.allocateDirect() so it would appear in [C-L1], but PooledByteBufAllocator would still allocate large chunks rather than 21,877 tiny allocations.)
  (c) Conversely, if the filter manually calls JDK ByteBuffer.allocateDirect(), it matches both [C-L1] and [N-L8] (#21877), but JDK DirectByteBuffer has no explicit release() method to "fix"—it is reclaimed by GC via Cleaner, meaning a leak requires retained strong references (or uncollected Old Gen objects, though CGC=8 shows concurrent Old Gen collection is running) rather than a missing release() call.
  (d) Note also that 21,877 live allocations in [N-L8] after only ~500 receipt uploads since 05:47 ([X-L8]) implies ~40+ leaked allocations per upload, with no explanation in [D-L4].

- Spring Boot Actuator JSON format errors ([C-L1], [C-L2]):
  (a) In [C-L1] (query ?tag=id:direct), Spring Boot's MetricsEndpoint strips already-applied filter tags from availableTags; therefore availableTags must be [], not [{"tag":"id","values":["mapped","direct"]}]. In [C-L2] (?tag=area:heap), area IS stripped from availableTags, making [C-L1] and [C-L2] inconsistent with each other.
  (b) Both [C-L1] and [C-L2] omit the standard "description" field returned by Spring Boot Actuator /actuator/metrics/{name}.
  (c) On Java 17, BufferPoolMXBean typically exposes a third pool ("mapped - 'non-volatile memory'", added in JDK 14) alongside "direct" and "mapped".

- Incomplete jcmd VM.flags output ([P-L4]):
  Real jcmd <pid> VM.flags always prints all ergonomic and default-modified flags (e.g., CICompilerCount, ConcGCThreads, G1HeapRegionSize, ReservedCodeCacheSize, SegmentedCodeCache, UseCompressedOops, UseCompressedClassPointers), not just the 5 listed flags.

- Incomplete jcmd GC.heap_info and NMT summary output ([H-L2], [N-L2]-[N-L9]):
  Java 17 GC.heap_info prints a class space sub-line beneath Metaspace ([H-L2]), and NMT summary prints mmap/malloc/arena sub-lines beneath every category, not solely under Other ([N-L8]).
